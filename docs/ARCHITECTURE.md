# Architecture

This document provides a high-level overview of the system architecture for the AI-Powered News Watch application.

## System Diagram

```
[User] -> [Web App] -> [API Server] -> [BullMQ]
                                      |
                                      v
[Worker] -> [Tavily] -> [Jina/Readability] -> [OpenAI] -> [Gamma] -> [Google Drive] -> [Gmail]
   ^           |             |                  |          |            |              |
   |           v             v                  v          v            v              v
   +-------[PostgreSQL]----[PostgreSQL]----[PostgreSQL]--[PostgreSQL]--[PostgreSQL]--[PostgreSQL]
```

## Components

-   **Web App:** A React-based single-page application that provides the user interface for creating and monitoring workflow runs.
-   **API Server:** An Express-based backend that exposes a REST API for the web app to interact with. It's responsible for creating new `Run`s and adding them to the job queue.
-   **BullMQ:** A Redis-based job queue that manages the asynchronous execution of the workflow.
-   **Worker:** A Node.js process that listens for jobs on the BullMQ queue and executes the workflow steps.
-   **PostgreSQL:** The primary database for storing all application data, including `Run`s, `Article`s, `Summary`s, etc.
-   **External Services:** A collection of third-party APIs that are used to perform the core tasks of the workflow.

## Data Model

The data model is defined using Prisma. The schema can be found in `prisma/schema.prisma`. The main models are:

-   `Run`: Represents a single workflow run.
-   `Source`: Represents a unique URL found by the search service.
-   `Article`: Represents the ingested content of a `Source`.
-   `Summary`: Represents the summarized content of an `Article`.
-   `GammaGen`: Represents a presentation generated by Gamma.
-   `DriveFile`: Represents a file uploaded to Google Drive.
-   `EmailLog`: Represents an email sent via Gmail.
-   `OAuthToken`: Represents a Google OAuth 2.0 token.

## Error Handling

-   Errors in the workflow are caught and logged in the `Run` record in the database.
-   The workflow is designed to be resilient, so an error in one step will not necessarily stop the entire run.
-   The Bull Board UI can be used to monitor and retry failed jobs.
